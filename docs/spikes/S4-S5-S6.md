# Spikes S4, S5, S6 — Subagent tree, readiness detection, plugin & MCP installs

- **Date:** 2026-10-28
- **Checklist:** M0-18 (S4), M0-19 (S5), M0-20 (S6)
- **Setup:**
  - macOS 26.5 (x86_64), Node 24.18.0, Claude Code CLI 2.1.293 (user install), Agent SDK 0.3.311, model `haiku`.
  - Every run used a scratch workspace.
  - Personal values (paths, account details) were masked or redacted before anything was written to this repo.

## S4 — Subagent attribution and agent tree

**Question:** can we tell which agent did what, live, for a prompt that spawns parallel subagents?

**Method:**
- `node packages/sidecar/scripts/spike-host.ts --scenario subagents --record raw.jsonl` prompts for two parallel
  subagents (one runs `ls`, one runs `date`).
- `scripts/make-fixture.ts` turns the raw stream into the committed fixture
  `packages/sidecar/test/fixtures/subagents-parallel.jsonl`.
- `normalize.test.ts` replays it.

**Results:**

| Check | Result |
|---|---|
| Subagents reported | 2 `system/task_started` messages with the spawning Agent call's `tool_use_id`, `description`, `subagent_type`, `spawn_depth` |
| Completion | 2 `system/task_notification` messages (`status: completed`) with `summary` and usage (tokens, tool uses, duration) |
| Attribution | All 10 subagent assistant/user messages carry `parent_tool_use_id` (= the Agent call) **and** `agent_id` |
| Subagent text | Arrives as whole assistant messages with `forwardSubagentText: true`. Only the main agent streams deltas |
| Live harness | 2/2 checks: both agents start and complete; 2 nested tool calls and 2 nested text messages attach to the right agent |
| Fixture replay | `normalize()` rebuilds the same tree offline (3 unit tests) |

**Findings:**
1. **`system/task_*` messages are enough to build the tree.** The `SubagentStart/Stop` hooks add nothing we need for
   the tree, so the app doesn't register them. The key for every node is the Agent tool call's `tool_use_id`.
2. **Subagents ran in parallel and in the foreground** (`run_in_background: false`). The main agent's final reply
   arrived after both task notifications.
3. **Raw recordings leak identity in encoded paths.** Claude Code turns paths into directory names
   (`/Users/jane` → `-Users-jane`), which plain path replacement misses. The recording also contained the user's own
   SessionStart hook output and a rate-limit event.
   - `fixtures.ts` therefore keeps an allowlist of message kinds, replaces plain **and** encoded paths and the username,
     and empties the init inventory.
   - `make-fixture.ts` refuses to write a fixture if any identity string survives.

## S5 — Install and auth detection

**Question:** can the app tell whether the CLI is installed, recent enough, and signed in, without reading anything
personal?

**Method:**
- `claude auth status --json` run in several states, with only field names and types printed.
- Logged-out, API-key and Bedrock states were simulated with an empty `CLAUDE_CONFIG_DIR`, so the real login was never
  touched.
- "Not installed" was simulated with a clean `PATH` and `HOME`.

**Results:**

| State | exit | `loggedIn` | `authMethod` | `apiProvider` |
|---|---|---|---|---|
| Subscription login | 0 | true | `claude.ai` | `firstParty` |
| Logged out | 1 (JSON still printed) | false | `none` | `firstParty` |
| `ANTHROPIC_API_KEY` set | 0 | true | `api_key` | `firstParty` |
| `CLAUDE_CODE_USE_BEDROCK=1` | 0 | true | `third_party` | `bedrock` |
| CLI not installed | — | (no CLI; `env.check` reports `path: null`, `ready: false`) | | |

- **Duration:** `claude auth status` takes ~0.45 s, and the full `env.check` (version, auth, git) about 1 s.
- **Not tested:** a Claude Console login, since the owner has no Console account. The mapping is generic (`authMethod` is
  passed through).

**Findings:**
1. **The JSON also contains `email`, `orgId`, `orgName` and `subscriptionType`.** `parseAuthStatus()` keeps only
   `loggedIn`, `authMethod` and `apiProvider` (ADR-0002), and a unit test asserts that the email never survives.
2. **`MIN_CLAUDE_VERSION` = `2.1.293`**, the oldest version verified with the app. Raise it when a release we depend on
   is required.
3. **The readiness screen works.** It shows a fix for each failing item: the install command per OS, `claude update`,
   or `claude auth login` to run in the user's own terminal, plus a Re-check button. The owner reached a session
   through it.

## S6 — Plugin and MCP installs, non-interactive

**Question:** can the sidecar install and remove plugins and MCP servers through the user's CLI without a TTY? What
does each step write?

**Method:**
- `node packages/sidecar/scripts/spike-install.ts --cwd <scratch>` runs in a fresh project folder.
- The `code-review@claude-plugins-official` plugin is installed and removed.
- An MCP server is added and removed at `local` and `project` scope.

**Results (6/6 on macOS locally; 6/6 on macOS, Windows and Ubuntu in CI):**

| Step | Result |
|---|---|
| Official marketplace configured | Already present on the machine. We never add marketplaces implicitly |
| `plugin install … --scope project --json` (no TTY, no `-y`) | exit 0 in ~1.9–2.5 s; one-line JSON `{"outcome":"ok",…}`; `.claude/settings.json` gets `enabledPlugins[id] = true` |
| `plugin list --json` | Lists the plugin with **`version: "1.0.1"`**, scope, install path and timestamps |
| `plugin uninstall … --scope project --json` | exit 0 in ~1.1 s; the entry leaves `enabledPlugins` |
| `mcp add/get/remove --scope local` | All exit 0. The entry is gone from `~/.claude.json` afterwards |
| `mcp add/remove --scope project` | Writes the server to `.mcp.json`, then removes it |

**Findings:**
1. **Plugin versions can't be pinned from the CLI.** `install` takes the marketplace's current entry. The bootstrap
   lockfile must record the installed `version` from `plugin list --json` and surface changes for review (CATALOG §7).
2. **`-y` is only needed for marketplace-declared commands.** For those, `--accept-command <sha256>` accepts exactly the
   command a previous `--json` run reported, which matches our pinned-trust model (ADR-0005). The installer never
   passes a blanket `-y`.
3. **Uninstall leaves the plugin's files in the CLI's cache** (`~/.claude/plugins/cache/…`, 36 KB here). Bootstrap
   rollback restores **project** files byte-for-byte. CLI-managed caches are outside its scope and are reported as such.
4. **List commands print multi-line JSON, while install and uninstall print one result line.** `parseJsonOutput()`
   handles both.
5. **3 OS in CI** (`.github/workflows/s6-install.yml`): Claude Code 2.1.293 from npm on fresh runners, the official
   marketplace added, then the spike. All 6 checks pass on macOS, Windows and Ubuntu
   ([run 40673510145](https://github.com/hafizhrf/AgentChainer/actions/runs/40673510145)).
6. **Windows + npm install = no `claude.exe` on PATH.** npm exposes a `claude.cmd` shim, which Node can't spawn without
   a shell. The first Windows run failed with "claude not found". `findClaude()` now resolves the shim to
   `node_modules/@anthropic-ai/claude-code/bin/claude.exe` (the package's `bin` on every OS).

## Decision

- No blockers.
- The agent tree comes from `system/task_*` messages keyed by the Agent call's `tool_use_id`.
- Readiness comes from `claude --version` plus three fields of `claude auth status --json`.
- Plugin and MCP installs go through the user's CLI at project or local scope, with the version recorded rather than pinned.
